# Mixed-session adoption and restart recovery (0.4.2)

The previous startup rule deferred a source with connections on multiple WANs
until that source had no relevant connections. Continuously active cameras,
TVs and smart appliances could therefore stay outside affinity indefinitely.

Both `sticky` and `affinity` now create a source mapping on the next eligible
new connection, even while mixed or unattributed old connections remain.
The first admission records the mapping before releasing the packet; simultaneous
arrivals reuse that choice. Existing confirmed connections and WAN-marked
connections keep their marks and NAT mappings. GUI pins, local/private/multicast
traffic, VPN exclusions and incoming-flow boundaries retain their precedence.

An unambiguous surviving WAN is still eligible for restart reconstruction.
For a mixed source the initial choice follows the normal weighted selector
in sticky mode, or its eligible deterministic preference in affinity mode.
Health remains a separate constraint: missing evidence cannot establish a
freshly eligible WAN. Sticky keeps its chosen WAN through recovery; affinity
can return future admissions to its preferred WAN.

## Connection state and mapping lifetime

Each tracked connection has an internal mapping membership identity. Older
mixed connections are tagged separately, and the observation merger preserves
membership across unconfirmed-to-confirmed migration. Confirmed kernel identity
changes do not inherit membership merely because a five-tuple was reused.

Only relevant members retain the mapping. A validated complete U-then-C view
must prove the last member ended before `IDLE_SECONDS=0` releases it; malformed,
partial, stale views and overlapping newer admissions retain the existing
safety rules. Older sessions neither block a new mapping nor resurrect one
whose members ended. A camera's original cloud connection can remain open on
WAN1 while all its new connections follow a new mapping on WAN0.

OPNsense generates gateway-pool rules with `sticky-address`; its pf lookup
reuses a source mapping or selects an address when none exists. The default
source mapping lifetime follows states referencing it. This update follows
that separation using Linux conntrack and the existing serialized admission
loop; it does not reproduce all pf routing or failover behavior.

## Helper restart

A bounded private checkpoint at `/tmp/wan-affinity/mappings.cache` stores source
choices and connection membership in RAM, with mode 0600. It contains connection
metadata, not credentials. It is updated after valid observations, mapping
changes and normal shutdown; it is never a flash-backed traffic journal.

Loading requires matching boot identity and mode/scope/seed, an age of at most
five minutes, a supported layout, bounded counts and an intact checksum.
Restoration follows a fresh complete connection observation. Saved entries
never create connection states: tuples, WAN evidence and confirmed kernel
identities must still match. A mapping without surviving members is not restored.

Malformed or missing caches fall back to fresh adoption while existing states
stay intact. A crash can lose membership updates since the last checkpoint;
uncertain matches are left as older connections and future admissions can make
a fresh choice. Reboot does not preserve this RAM cache. Optional post-idle
retention without surviving members is not restored across helper restarts.

## Validation

The C engine/checkpoint suite passes 270 checks and the bounded-worker suite
passes 21. AddressSanitizer and UndefinedBehaviorSanitizer cover the engine
and cache paths. The Python reference suite passes 102 tests, including both
selectors with continuously active mixed and unattributed old sessions.

The opt-in Mac mini driver ran beside the production LAN-wide service. In each
mode two HTTPS connections were established on different WANs before the private
helper started. Sixteen concurrent new HTTPS connections shared the selected
WAN. Restarting the helper restored the same mapping with 16 surviving members;
two further new connections followed it. The original two kernel identities,
marks and NAT addresses remained unchanged throughout.

The final run verified restoration of the client's GUI pin, routing rules,
firewall rules and startup-hook bytes. Only live firewall counters and generated
timestamp comments were excluded from the rule comparison. Production affinity
and watchdog PIDs were retained. The shared-health consumer test also passed
633 checks using a private socket. Physical WAN outages and router reboot were
not manufactured; broader platform limitations remain in the qualification guide.

The guarded production upgrade then installed the same 0.4.2 executable in
sticky mode with the existing LAN-wide configuration. Both WANs remained
eligible, the health socket stayed connected, and the queue was empty with zero
drops. The initial check showed new mixed-source mappings for cameras, a
doorbell and a FireTV while their older states remained tracked separately.
Original pins, routing/mangle rules, configuration bytes, startup hooks and
the watchdog PID were unchanged. Eight additional LAN-bound HTTPS/DNS/QUIC
checks passed from the Mac mini after the upgrade.
